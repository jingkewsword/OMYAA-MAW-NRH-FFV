# Linux 托管运行环境 Python 版本修复

## 问题与最小方案

Linux/macOS 打包版原先放行任意 Python 3.11+，再用系统 `python3` 创建 venv，
却把规格中的 `3.11` 写成已安装版本。当前锁文件中 Torch cu130 的 cp313/cp314
wheel 缺少 hash，导出清单只包含其他 wheel 的 hashes；官方索引对应链接也没有
提供 sha256，因此这些环境可能在下载后才遇到 hash 不匹配。
客户没有提供完整安装日志，尚未最终确认其首次失败的包是否就是 Torch。

本轮沿用三个 Runtime 已声明的 Python 3.11 基线，不扩大为 Python 3.14 支持：

1. `maw/runtimes/base.py`：创建或修复前优先寻找 `python3.11`，再检查默认
   `python3` 是否确实为 3.11；找不到时提前提示，不清空已有环境、不下载依赖。
2. 创建 venv 后实测其解释器版本；实际版本不匹配时停止。安装记录保留实测版本，
   检测不到时保留未知，不回填期望值。已有 ready 环境也核验实际版本。
3. `maw/local_runtime.py`：设置中的已安装 Python 版本来自当前解释器检测，
   不再信任旧安装记录中的固定值。
4. 更新用户指南与定向测试；依赖版本、锁文件和 hash 校验机制保持不变。

## 验证计划

- 系统默认 3.14、同时有 3.11：使用 3.11 创建环境，记录完整真实版本。
- 只有 3.14：创建、清空和依赖安装之前失败，保留原目录与安装记录。
- 创建出的 venv 仍是错误版本：停止安装并记录真实版本。
- 旧记录写 3.11、实际为 3.14：界面显示 3.14，状态要求修复。
- 版本探测失败：显示未知，不能显示规格中的 3.11。
- 运行 Runtime / 本地 / OCR / MOSS 定向测试、相关 GUI 测试与静态检查。

真实 Linux AppImage 安装、Torch 下载和模型推理需要单独验收；Windows 模拟测试
不作为跨平台或 Python 3.14 支持证明。

## 提交前审查

审查未发现阻塞本轮修复提交的问题：

- 3.11 限制只作用于打包版 Unix 托管环境，源码模式继续使用开发解释器，Windows
  继续使用内嵌解释器。三个 Runtime 的现有冻结基线均为 3.11。
- 缺少匹配版本的预检发生在修改安装记录和清空旧 venv 之前；预检失败保护旧环境。
- 新建 venv 再次核验实际版本，覆盖复用旧解释器、启动器版本与生成结果不一致的情况。
- 版本探测使用独立 Python 模式、恢复宿主动态库路径并限时 5 秒；失败返回未知。
- 已有 ready 环境也检查实际版本，避免旧记录的固定值继续冒充实测结果。
- Python 3.14 支持属于后续兼容工作，本次没有通过移除 hash 来扩大支持范围。

已核对 fork 默认分支为 `main`，远端基线与本次基线相同，目标分支尚未存在。
