# FFprobe 失败的分层回归

起点 `f233b532`。维护者要求保留上层 mock，补齐 MAW 对 FFprobe 报错的处理和少量真实坏文件集成保障，核对相关改动与发布触发，验证后更新 PR #2 并保持 Draft。

## 责任与改动

上阶段同 92 项的 87→0 次 FFprobe、33.909→15.020 秒是历史单次 A/B。它证明重复准备成本下降，原 93 方法/断言 AST 不变证明用例保留；两者都不能单独证明异常转换覆盖相同。原始真实探测能偶然检出包装函数不再捕获异常，上层 mock 后这个责任必须另行明确。

| 层 | 实际运行与断言 | 独有故障边界 |
| --- | --- | --- |
| 上层服务器 common | 原 91 项及已有断言保留，逐例 mock 探测 None、缩略图未就绪；元数据合并、绑定、HTTP、文件、备份、锁与线程保持真实 | 已知媒体状态下的 MAW 业务行为；不负责检查 FFprobe 异常转换 |
| 探测包装 common | `test_media` 新增 2 方法，音轨/帧率各覆盖子进程非零退出、超时、OSError，以及空字符串/损坏 JSON；执行真实 MAW 包装逻辑，只模拟 subprocess，断言调用发生且返回 None | MAW 必须将探测错误转换成未知状态，不能向加载/保存调用者抛出；与成功确认无音轨的 [] 分开 |
| 真实兼容 media | 新模块 `test_ffprobe_failure_integration` 的 2 方法，在私有临时目录写入不可解码 MP4，启动实际 FFprobe，观察实际命令和非零退出；音轨/帧率均返回 None | 实际所用 FFprobe 对坏输入报错，MAW 包装器能接住；不模拟进程结果或异常 |
| 真实业务链 media | 上述第二方法继续加载工程，断言没有伪造 media_metadata、缩略图未就绪，通过真实 HTTP 修改并保存字幕；核对备份等于原工程、磁盘与内存文本一致、源媒体字节不变 | 真实探测失败后工程仍可保存和备份，而不只是包装函数单独返回 None |

没有新增生产代码、放宽断言、skip 或时限。真实集成的 subprocess spy 只观察实际执行并重抛实际异常，不提供假 stdout/退出码。HTTP 服务器逐例隔离并在清理时 shutdown/join；坏媒体不共享可变文件。

## 触发与依赖

- 新模块登记到现有 `MEDIA_MODULES`；两个快速方法继续 common，不增加新门禁种类。
- 新选择回归核对 `maw/media.py`、`maw/ffmpeg.py`、`maw/project_io.py`、`server-editor/serve.py`、发布工作流和新测试模块会选择 media，准备真实媒体依赖，命令带 `--required`；发布模式包含 media，纯 README 不包含。
- 实际检查 `.github/workflows/editor-checks.yml`：PR 按事件 base 选择门禁；共享工作流/依赖/锁触发宽范围。检查 `release.yml`：Linux test-quality 安装 FFmpeg 并显式运行 required media；各平台媒体验证使用对应工具，质量与完整浏览器成功后才进入打包和发布。没有实际执行发布。
- 缺少 FFprobe 可报告依赖 skip，但 required 执行器会失败；未把此 skip 登记为平台不适用。已有完整发现测试继续核对所有 Python 用例归属唯一且无丢失。
- 仓库外独立升级 FFmpeg 不会产生提交事件；需提交对应版本/安装配置或在发布验证中执行 media。此处保障 MAW 对所用工具的失败契约，不穷举 FFprobe 自身解析器的所有格式。
