# 测试治理

本页面向测试与 CI 维护者。目标是缩短一次修改到可信反馈的等待时间。以下原则也是后续实现的验收准则；可用命令见[调试工作流](DEBUG_WORKFLOW.md)，一次运行的实际范围以计划和报告为准。

## 维护目标与验收原则

- 测试保护当前支持的用户流程、体验和代码契约，包括本次影响的打开、编辑、撤销、保存重开、导出、取消及失败恢复。断言必须有现行行为依据，不能为保留旧断言而倒改正确的产品行为。
- 开发与修复默认验证改动及其直接、间接消费者。Python、Node、浏览器和 CI 使用同一份影响判断。领域代码附带文档、日志或 CHANGELOG 时，取实际消费者的并集。
- 文档也是程序输入。保留导航、离线说明、发布说明和网站等实际消费者检查；普通文档变动本身不构成运行应用全量的理由。
- 发布前、广泛共享契约或依赖改变，以及确实无法可靠界定影响的场景，才执行必要的整体回归，并记录理由。普通 push、功能更新或测试治理提交不自动要求全量。
- 已确认失效的断言和退役用例可删除；同平台、配置、行为和产物已证明等效的重复执行可合并。保留原用途及剩余保障的说明。有价值但夹具、隔离或观察时点错误的测试应修正，尚未判清的失败保留证据。
- 必要全量应尽量完成所有独立检查，保存真实退出码和完整失败清单，最后统一失败。前置准备失败只阻塞实际依赖范围，不能使其他独立检查无声消失。
- 本次执行、复用结果、失败、阻塞和未运行应明确区分。缺报告、缺分片、额外跳过、超时和预算耗尽不能冒充完整通过。终端摘要不代替完整错误记录。
- 接续应从完整文件或独立分组边界恢复。复用前验证代码、测试、夹具、配置、工具链与输入；受影响旧结果失效。中断中的单元使用干净夹具重跑。接续能力须有中断、失效和缺结果验证，才能作为可用功能说明。

## 当前选测与执行边界

`scripts/local_test_impact.py` 合并源码引用、直接与间接消费者，以及动态装配所需的领域检查。计划包含具体 Python、Node、浏览器文件、准备需求和扩大范围的理由。动态加载不能仅靠静态引用证明；共享装配、未知路径或不可确认的差异会保守扩大到相关领域，必要时明确选择完整集合。

`scripts/ci_impact.py` 在 PR 合并提交与事件基线一致，或 push 的 before 提交可验证为祖先时，使用可信差异生成同一计划。差异不可验证时保留原因。文档与源码混改仍按并集执行。

现有 CI 按平台职责消费计划：Ubuntu 执行选中 Node 和浏览器；PR 的选中 Python 由 Windows 执行，Ubuntu 保留原有相关契约；push 的选中 Python 在 Ubuntu 执行。原两平台调试工具和 Windows 生命周期保障按实际交集保留。Windows 预览只在应用或打包影响需要时执行原有显示、Launcher、打包与启动检查。该平台分工不代表每个选中测试都在所有平台执行。

浏览器按选中集合分片，小范围默认一片；完整集合或较大范围可增加分片。每片保存完整发现、分片发现、实际结果和提交对应的回执。汇总核对分片无重叠、并集完整、配置一致和结果有效，缺片不能通过。浏览器与其他独立层可以并行。

本地显式 `--pack`、`--layer` 或开发核心只验证指定范围；`--plan-only` 不执行测试。本地通过不代表 GitHub CI、跨平台安装包或人工体验已经验收。`--required` 是运行器的严格集合约束，不表示 GitHub 已配置同名必需状态。

## 失败、清理与后续能力

修复先复验失败项，再验证修改的实际消费者与相关关键流程。既有证据适用于其记录的代码、平台和配置；没有相关变化及新疑点时，不为整理报告重复整库运行。

独立组继续执行、完整错误汇总、文件或分组检查点和同输入接续按上述原则验收。具体上线范围以[调试工作流](DEBUG_WORKFLOW.md)中的现有命令为准；不把设计中的参数或跨提交智能复用当作已实现功能。

当前执行器会逐组保存状态和完整失败清单，已选独立组失败后仍继续；前置准备以实际文件消费者判断阻塞。CI 分片汇总保留各片的所有失败及缺结果问题。文件/分组级自动中断接续尚待实现，已有进度报告本身不等于可以安全复用旧结果。
